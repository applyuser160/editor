# ADR-0002: Ropey（Ropeデータ構造）によるテキストバッファ管理の採用

- **ステータス:** Deferred（現行実装では未採用）
- **決定者:** Syun
- **決定日:** 2026-08-22
- **見直し日:** 2026-08-27
- **実装状況:** [現行の編集コアはMonaco Editor](../implementation-status.md)であり、`ropey`は依存関係に含まれない。

---

## コンテキストと問題提起

テキストエディターのコア性能は、テキストバッファのデータ構造に大きく依存します。  
巨大なファイル（100MB〜数GB）を開いた際でも、メモリ再確保による遅延を防止し、任意の位置への高速な挿入・削除、行・文字単位でのランダムアクセス、マルチスレッドでの安全な読み取りを可能にするデータ構造が求められます。

---

## 検討した選択肢

1. **Rope（Ropey クレート）**
2. **Piece Table（VS Code 方式）**
3. **Gap Buffer（Emacs 等で採用）**
4. **Line Array / Vector of Strings**

---

## 決定結果

**この方針は延期します。** 現行リリースのテキスト編集は Monaco Editor に委ねています。Ropey の導入は、ネイティブ編集コアへの移行を設計・検証するまで実施しません。

### 決定理由

- **不変クローンとマルチスレッド安全性:** `Ropey` は内部で B-Tree ノードの参照カウント (Arc) を利用しており、O(1) で不変スナップショット（Clone）を生成できます。これにより、UI スレッドで編集しながら、バックグラウンドスレッド（LSP, Tree-sitter, 検索）へノーロックでバッファ状態を渡せます。
- **O(log N) の挿入・削除:** ギガバイト級のファイルでも、テキストの挿入・削除操作が局所的なノード分割/統合のみで完結し、全体コピーが発生しません。
- **UTF-8 / UTF-16 相互変換の最適化:** バイトインデックス、文字インデックス、行インデックスの双方向検索が O(log N) でキャッシュされ、LSP (UTF-16) と Rust (UTF-8) の座標変換が極めて高速です。

### 肯定的な結果

- 巨大ファイルの読み込みおよび編集がミリ秒単位で完了。
- 非同期構文解析や検索エンジンとの統合が容易。

### 否定的な結果・トレードオフ

- 単純なフラットメモリバッファに比べ、連続メモリ領域としてのポインタ走査にチャンク境界の考慮が必要。
